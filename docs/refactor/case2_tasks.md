# 案例二任务清单：Qwen2.5-7B 张量并行推理规划

## 使用方式与范围

目标：解释一个语言模型的推理请求如何产生逐层通信，GPU 显存、KV cache、网络带宽和请求状态如何共同约束部署与故障处理。

这是一份可以单独作为主线执行的任务清单，**不要求三个人两天同时完成两套生产级系统**。案例一与案例二共享拓扑、事件引擎、容量约束、接口、持久化和权限；这些共享任务只做一次。建议主线选案例一；若选案例二作为主线，用本文替换案例一的工作负载与实验部分。

首版范围：Qwen2.5-7B-Instruct；TP=1/2/4；固定请求输入/输出长度；每个模型副本一次处理一个请求；多个副本可并行；静态预留请求最大长度对应 KV；模型层内采用标准 Megatron 式两次 AllReduce 抽象。**没有实现 vLLM 连续批处理、PagedAttention、KV 迁移或精确 kernel 性能模型，不应使用这些名称描述已有能力。**

- **A：你——模型结构、推理语义与最终集成判断。**
- **B：组员一——资源/通信、放置、对照实验与性能权衡。**
- **C：组员二——接口、状态证据、界面与正式交付。**
- 单人任务可独立验收；联调仍由一人主责。每项工时是基于本轮重构基线的核验和补全预算，非从零开发承诺。P0 约 A 8.75、B 8、C 10.5 人时；各留 2 小时缓冲。真实 GPU 测量单列 P1。
- 状态必须以实际文件和测试结果为准：代码基线存在≠实测完成。尤其 `SYNTHETIC` 计算时间不能改标签冒充 `MEASURED`。

评分简称：架=架构 25；复=复杂性管理 25；域=领域准确 25；析=分析权衡 15；码=代码 10；演=现场演示额外 15。

## A 的任务：模型与请求语义

### T01｜冻结部署问题和比较口径

- **P0｜A 单人｜0.5 小时｜评分：域、析｜类型：设计核验**
- 输入：课程要求、共同实现合同、TP 首版范围。
- 产物：问题陈述；明确研究单请求延迟、请求容量还是固定八卡预算下的吞吐，分别设计实验。
- 验收：不把“一个 TP4 副本”和“四个单卡副本”的总吞吐直接当相同资源利用方式的单请求加速；所有比较写清 GPU 预算、请求集和排队策略。

### T02｜核对模型结构与合法切分

- **P0｜A 单人｜0.75 小时｜评分：域、码｜类型：代码核验**
- 输入：Qwen 官方配置、`packages/fabric-sim/src/fabric_sim/tp.py`。
- 产物：28 层、hidden=3584、28 Q 头、4 KV 头、head_dim=128、权重精度与参数量来源表。
- 验收：常规均匀切分仅接纳模型支持的 TP；首版明确支持 1/2/4。TP=8 不能仅因硬件有八张卡就放行。若权重字节用 7.61B 近似参数量推导，应保留估计标签，不写成逐张量精确计数。

### T03｜核对 KV 和显存准入公式

- **P0｜A 单人｜1.5 小时｜评分：域、复、码｜类型：代码核验**
- 输入：T02、上下文长度、dtype、workspace 与显存保留量。
- 产物：每 token KV 推导和边界测试；准入理由结构。
- 验收：BF16 K/V 的全模型原始 KV/token 为 2×28×4×128×2=57,344 bytes，即 56 KiB；TP4 均匀切分为每卡 14 KiB/token。每卡需求还包括分片权重、运行开销；不能只算模型权重或把所有显存都简单除以 TP。

### T04｜核对 prefill/decode 的执行与通信依赖

- **P0｜A 主责，B 提供集合通信｜2 小时｜评分：域、复、码｜类型：代码核验**
- 输入：T02–T03、请求 prompt_tokens/max_new_tokens、core ring。
- 产物：逐层执行轨迹、首 token 和后续 token 测试。
- 验收：prefill 的激活规模随输入 token 数变化，decode 一次新增 token 的规模不同；每层两次 AllReduce 的前后依赖成立；TP1 不产生跨卡 collective；第一输出 token 来自 prefill，不多算一轮 decode；`max_new_tokens=1` 仍有合理 TTFT、没有虚构后续 token 时延。

### T05｜定义计算 profile 与单位来源

- **P0｜A 单人｜1 小时｜评分：域、析｜类型：模型核验**
- 输入：T02–T04，TP1/2/4 的计算时长配置。
- 产物：profile 文件与假设列表。
- 验收：区分结构推导和经验时间；不默认 TP 翻倍便将所有计算时间精确除二；所有时长 finite、非负、有上限。缺乏实测时保留 SYNTHETIC，性能结论仅适用于所设参数，并做敏感性分析。

### T06｜核对副本故障和请求终态

- **P0｜A 单人｜1.5 小时｜评分：复、域、码｜类型：代码核验**
- 输入：运行中请求、TP 分配、节点/链路故障、epoch。
- 产物：整个 TP 副本失效的状态机和负例。
- 验收：一个 rank 失效影响整个副本；在途请求显式失败，不凭空保留 KV 无损续写；若以后支持从 prompt 重试必须另设尝试号和重复输出规则。取消流、释放请求 KV、忽略旧事件；排队请求可由仍健康的副本处理。

### T07｜冻结可复现请求集与对照输入

- **P0｜A 主责，B 联调实验｜1.5 小时｜评分：域、析｜类型：实验设计**
- 输入：T01–T05、模型与仿真上限。
- 产物：短/长输入、不同输出长度、并发到达和故障请求集；记录同一批请求 ID。
- 验收：固定请求长度分布和到达轨迹；正常、过载和显存拒绝分开；不同策略使用同一请求集。采样 token 内容不影响当前长度驱动仿真时，应明确该模型没有模拟输出质量和 EOS 语义。

### T08｜获取真实推理与通信 profile

- **P1｜A 单人，B 复核统计｜2.5 小时起｜评分：域、析｜类型：真实 GPU 待执行**
- 输入：已经能运行的模型环境、合法 TP、受控请求集；先检查磁盘/缓存与可用显存。
- 产物：实际模型/框架版本、GPU ID、请求长度、TTFT、后续 token 时延、显存与原始样本。
- 验收：环境已有才推进；安装或下载长时间受阻则停止。测到的是实际框架整体表现，不能拿总延迟强行反推每层通信；单机 NUMA 结果不冒充跨机架实测；没有运行则明确 NOT_RUN。

## B 的任务：通信网络与资源权衡

### T09｜核对共享拓扑及单机/多机边界

- **P0｜B 单人｜0.75 小时｜评分：架、域｜类型：共享代码核验**
- 输入：共同 core、合成拓扑、用户八卡机器的拓扑信息。
- 产物：GPU→物理资源路径图及参数来源。
- 验收：同机通信不是零成本；NIC/上联容量归属于共享资源；单机两 NUMA 组与合成 Leaf–Spine 分开。若案例一已经完成此项，只复核 TP 的路径调用，无需重写 core。

### T10｜核对容量共享与通信结束时刻

- **P0｜B 单人｜0.75 小时｜评分：复、域、码｜类型：共享代码核验**
- 输入：core 活跃流/事件引擎、T09。
- 产物：两个副本同时通信的容量与完成时刻检查。
- 验收：总速率不超过方向资源容量；一个流结束后重新分带宽；未经过启动延迟的流不提前传输；通信依赖不能因接收了旧 epoch 事件而提前结束。

### T11｜核对 TP 激活量与集合通信次数

- **P0｜B 主责，A 核对模型语义｜0.75 小时｜评分：域、码｜类型：代码核验**
- 输入：T02、T04、固定 Megatron 式抽象。
- 产物：每层 payload bytes 与通信次数的手算/代码对照。
- 验收：每次 payload 按实际仿真定义由 token 数×hidden×激活字节得到，再使用 ring 因子计算物理发送量；明确这是激活部分结果，不是训练梯度、模型权重或默认交换全部 KV；多余的 embedding/logits 操作未建模则列为局限。

### T12｜实现或复核显存合法的副本放置

- **P0｜B 单人｜1 小时｜评分：复、域｜类型：代码核验**
- 输入：T03、GPU 容量、replica GPU IDs。
- 产物：副本合法性检查、资源冲突和内存不足的原因。
- 验收：一个副本使用恰好 TP 张健康 GPU；不同副本不重复占卡；权重常驻占用不随请求结束被误释放；请求 KV 在结束/失败后释放；额外卡数不意味着请求必然更快。

### T13｜运行两个副本共享链路的实验

- **P0｜B 单人｜1.25 小时｜评分：域、析、演｜类型：实验待复跑**
- 输入：两个 TP2/TP4 副本，互不重叠 GPU，明确共同上联路径；同一请求集。
- 产物：独占/并发的 TTFT、完成时间、链路曲线。
- 验收：从实际路径证明竞争；同卡数同输入仅改变另一副本是否运行；不把排队时间、prefill 计算和通信等待混成一个不能解释的加速比。

### T14｜运行上下文长度与 KV 准入实验

- **P0｜B 主责，A 核对公式｜1 小时｜评分：复、域、演｜类型：实验待复跑**
- 输入：T03、固定模型与 TP、逐步增加 prompt+最大输出预算或降低显存配额。
- 产物：可接纳/拒绝边界、已用/已预留 KV 曲线或表。
- 验收：首版采用最坏长度预留，虽然当前 KV 少也可能因为预算不足拒绝；图上区分 current 与 reserved；请求结束后预留释放；显存失败给具体不足量。改变配额是合成约束测试，不声称在3090上发生了实际 OOM。

### T15｜比较 TP=1/2/4 与副本数量

- **P0｜B 单人｜1.5 小时｜评分：析、域｜类型：对照分析**
- 输入：T07、对应计算 profile、同一拓扑。
- 产物：两张不同口径的表：单副本固定请求的延迟；固定 GPU 总预算下各部署方式的队列/吞吐。
- 验收：单请求延迟与总吞吐不能混用；不预设 TP4 最快；TTFT 与后续 token 时延分开；容量和网络收益都写清。若某配置内存不可行就报告不可行，不删掉失败行。

### T16｜分析敏感性、规模和遗漏因素

- **P0｜B 单人｜1 小时｜评分：析、码｜类型：性能分析**
- 输入：链路带宽/延迟、profile、请求数与事件数。
- 产物：单因素敏感性表、仿真 CPU 耗时与事件数、简化影响说明。
- 验收：区分模拟推理延迟与运行仿真器的实际耗时；指出没有连续批处理、KV分页、算子融合及精确重叠时，结论适用范围有限。确定性重复不能伪造统计显著性。

## C 的任务：可复现服务与展示

### T17｜核对 v2 API 与输入边界

- **P0｜C 单人｜1.5 小时｜评分：架、复、码｜类型：接口核验**
- 输入：共同 API 合同、TP demo 与 T07 请求集。
- 产物：提交/查询/事件的真实 HTTP 记录，非法 TP/长度/副本重叠输入的错误记录。
- 验收：接口使用 scenario=tp 明确进入 TP adapter，不套用 DDP 的梯度字段；错误输入得到明确响应；服务器接受仿真与业务请求能否完成是不同状态。

### T18｜核对不可变快照和持久状态

- **P0｜C 单人｜1 小时｜评分：复、码｜类型：存储核验**
- 输入：T17、SQLite、input_hash。
- 产物：输入冻结、历史结果可读、服务中断状态检查。
- 验收：调整 TP 或 prompt 后另建运行，旧结果不变；每条解释与图都绑定运行 ID；重启不声称自动恢复 GPU 推理；归档不包含本机凭证。

### T19｜核对角色权限与只读边界

- **P0｜C 单人｜0.75 小时｜评分：复、码｜类型：安全核验**
- 输入：viewer/editor 策略和 v2 路由。
- 产物：匿名/只读/编辑状态码矩阵。
- 验收：viewer 能看与解释既有结果，不能改变配置或启动新仿真；故障输入仅描述模拟事件，不执行系统命令；说明共享角色不等于多租户身份管理。

### T20｜让 Assistant 解释具体请求和约束

- **P0｜C 主责，A/B 复核｜0.75 小时｜评分：域、复、演｜类型：功能核验**
- 输入：T13–T15、故障结果。
- 产物：解释 TTFT、KV 拒绝、TP 不合法、故障请求失败的案例。
- 验收：每个结论引用实际请求/副本/资源或计算量；没有足够证据时不归因；不将“传激活”解释成“传梯度”；规则解释器如实标注，不宣称已集成 LLM Agent。

### T21｜完善推理场景演示视图

- **P0｜C 单人｜1.5 小时｜评分：架、演｜类型：界面核验**
- 输入：T17–T20、workload 页面。
- 产物：TP、输入/输出长度、显存配额、故障情景的操作入口；请求状态与指标显示。
- 验收：能看到排队/prefill/decode/完成或失败；TTFT 单位正确；只生成一个 token 时后续 token 指标显示不适用；明显标注仿真与参数来源，事件回放不伪装真实模型输出。

### T22｜集成负例与资源释放验收

- **P0｜C 主责，A/B 修各自模块｜1.5 小时｜评分：复、域、码｜类型：集成实验**
- 输入：T03、T06、T12；接口运行结果。
- 产物：故障在 prefill、decode、通信启动延迟期间的测试；释放与旧事件检查。
- 验收：在途请求明确失败，无幽灵 token；释放 KV 不释放其它副本权重；健康副本继续；服务查询/解释可用；重复查询不推进模拟状态。

### T23｜制作图示与正式报告

- **P0｜C 整理，A/B 分别供稿｜2 小时｜评分：架、复、域、析｜类型：联合交付**
- 输入：最终代码、T01–T22、课程模板。
- 产物：组件图、Model/Replica/Request/Resource/Run 数据图、请求状态机、副本故障时序；8–12 页报告与 PPT 更新清单。
- 验收：描述实际“每副本单请求、静态 KV 预留”的实现，不画成连续批处理；所有数值有来源；在报告权衡中说明静态预留更易保证不超显存，但利用率较低。

### T24｜干净环境复现与演示排练

- **P0｜C 主责，全员验收｜1.5 小时｜评分：码、演｜类型：最终交付**
- 输入：最终代码、README、证据和版本号。
- 产物：另一台电脑上的启动/复跑记录、Git 提交与可访问链接、录屏、每人的答辩题。
- 验收：仿真演示不依赖下载模型权重；真实测量结果单独标注；展示合法/非法 TP、正常请求、KV 准入和副本故障；全员解释自己模块及一个相互影响案例。外部仓库仍需实际发布与权限确认。

## 实验矩阵与交接时点

| 实验 | A 提供 | B 执行/解释 | C 留证与展示 |
|---|---|---|---|
| TP 合法性与激活量校验 | 结构约束和公式 | 字节与通信次数核对 | 非法输入状态码、结果表 |
| 上下文长度/KV 准入 | KV 公式与预算语义 | 长度或显存配额单因素实验 | current/reserved 区别与拒绝理由 |
| 两副本共享链路 | 相同请求集 | 独占/并发对照 | 带宽曲线与 TTFT 对比 |
| TP1/2/4 部署选择 | 各 TP profile 来源 | 固定请求/固定 GPU 预算分别比较 | 不可行行与假设一起展示 |
| 副本故障 | 请求失败/取消语义 | 确认受影响资源与健康副本 | 状态时间线、无幽灵 token 负例 |

开始后 1 小时冻结合同；第一天中午通过结构、显存和字节量核对；第一天结束至少有正常请求、KV 拒绝及一次故障终态；第二天中午停止扩功能，整理证据与报告。若 GPU 模型环境未就绪，不阻塞流级仿真；若 TP adapter 还不稳定，以已验证 DDP 主线交付，TP 只展示边界明确的设计，不装成完整实现。
