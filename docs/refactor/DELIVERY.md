# 重构交付说明与验收状态

## 本次重构的主问题

给定具体 AI 工作负载，GPU 的物理放置与有限通信资源怎样影响完成时间；节点或通信资源失效后，哪些作业/请求受影响，如何保证资源分配、进度和结果语义仍然一致？

原项目位于用户提供的 `数据通信网络/gpu`。本交付在独立副本上完成，保留原目录；已有动态仿真基线经本次审计、修正和复测后交付。不能将项目中所有既有代码都归为本次新写。

## 从原项目到 v2

| 原有做法 | 重构后的做法 | 主要路径 |
|---|---|---|
| 抽象通信模式 + 固定需求速率 | 模型 profile → 梯度或激活字节 → 分阶段集合通信 | fabric_sim/ddp.py、tp.py |
| 静态负载与带宽代理值 | 全局事件时钟、剩余字节、活动流速率、时间线 | fabric_sim/core.py |
| 同节点通信省略 | 有限共享本地资源，与跨节点 NIC/上联区分 | Network.path |
| GPU 重新分配作为恢复 | DDP 整组取消→完整检查点回滚→等待→加载→重启 | ddp.py |
| 单一作业抽象 | DDP Job 与 TP Replica/Request 分开，公用网络引擎 | ddp.py、tp.py |
| 主要围绕静态规划页面 | 新工作负载页面 + 异步API + 冻结输入/持久结果 | /workload、simulation_api.py |
| 未明确区分真实与模拟 | 结构推导、合成设定、设备实测来源分别标记 | profile、measurement_status |

旧 v1 页面与模块为兼容保留；新主线没有沿用旧 worker 分片汇总方法。不同模型的通信流必须在同一情景内共同受到共享容量约束。

## 三类复杂性及验收反例

- 结构：负载 adapter 与资源引擎分离，DDP/TP 共用 Engine；不把网页代码当仿真逻辑。
- 行为：整组准入、请求/作业状态机、故障取消、epoch、不可变输入。旧计算完成事件不得推进重启后的任务。
- 语义：DDP 各卡完整模型，TP 权重分片与 KV 显存分别计算；训练梯度与推理激活不混用；业务不可行不是服务器执行异常。

## 仍须明确的边界

网络是两级有效容量资源抽象，没有完整 Leaf–Spine 交换机图、ECMP、备选路径计算。故障分析支持节点/方向资源失效及恢复，但不等于自动网络绕路。本轮优先做容量约束与工作负载状态的自洽；若老师要求路由层重规划，应将图路径与备选路由列为下一步领域扩展。

`compact` 与 `first_fit` 当前共用相同顺序选择逻辑，不可声称算法优劣；先比较固定 compact/spread 放置的因果差异。DDP 观察结束时间不同于作业 makespan。TP 平均时延只看成功请求，故障场景还须一起展示失败数、未完成数和观察窗口。

检查点开销采用延时参数，尚未模拟 checkpoint 存储网络竞争；TP 未连续批处理或无损迁移。只读 Assistant 是规则解释器；NATS、多协调器、高可用、真实训练/推理均不在已验证主链。
