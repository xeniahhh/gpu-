## 1. TP 大小与 TTFT

| 配置 | 首个请求 TTFT | 双请求平均 TTFT | 仿真结束时刻 | AllReduce 调用 |
|---|---:|---:|---:|---:|
| TP1 | 19.200 ms | 45.800 ms | 110.400 ms | 0 |
| TP2 | 15.079 ms | 34.003 ms | 79.695 ms | 448 |
| TP4 | 16.683 ms | 39.636 ms | 95.815 ms | 448 |

首个请求 TTFT 从请求到达起算，三组都在同一时间起步，因此适合比较当前 TP 配置本身。双请求平均 TTFT 还包含同一副本第二个请求的排队时间，适合描述本实验工作负载下的端到端表现。两种口径下当前 TP2 都最低。

TP4 缩小了每卡权重占用，但增加参与集合通信的 rank 数量；结果仍受设定计算时间和网络负载限制。该排序不能外推为真实 Qwen 在任意 GPU、NVLink 或跨 NUMA 配置上的性能。

比较口径：固定模型、首个请求长度、TP 组内 GPU 资源和输出 token 数，只改变 TP 大小。双请求组中的第二个请求会排队，不能把它当作纯 TP 计算加速比。

## 2. 两副本共享网络竞争

| 请求 A 的对照 | TTFT | 尾时延 |
|---|---:|---:|
| A 独占副本 | 36.061 ms | 66.974 ms |
| A 与 B 同时运行 | 44.282 ms | 75.387 ms |

TTFT 增至 1.228 倍，尾时延增至 1.126 倍。两组保持请求长度、TP 大小和显存准入不变，只改变竞争者是否存在，因此能说明配置中的共享上联发生资源争用。

这里的尾时延取仿真窗口内最后完成时刻。它用于同配置对照，不应与其他请求集或不同输出 token 数的绝对时延直接比较。

## 3. 带宽敏感性

| 上联带宽 | 平均 TTFT | 最后完成时刻 |
|---:|---:|---:|
| 25 Gbps | 60.723 ms | 92.214 ms |
| 50 Gbps | 44.282 ms | 75.387 ms |
| 100 Gbps | 36.061 ms | 66.974 ms |

从 25 到 100 Gbps，平均 TTFT 下降 40.6%。这说明在给定流量和放置下，网络容量确实进入请求时延模型。其他带宽值、真实拥塞控制和小消息行为尚未测量。

## 4. 请求量扩展

| 请求数 | 完成数 | 平均 TTFT | 最后完成时刻 | 处理事件数 | 结果大小 |
|---:|---:|---:|---:|---:|---:|
| 2 | 2/2 | 44.282 ms | 75.387 ms | 4484 | 5.13 MiB |
| 4 | 4/4 | 81.975 ms | 150.774 ms | 8968 | 10.25 MiB |
| 8 | 8/8 | 157.362 ms | 301.548 ms | 17936 | 20.51 MiB |

请求数从 2 增至 8 时，平均 TTFT 增长 255.4%，处理事件与结果大小约按请求数增长。原因是每副本一次只处理一个请求。该实验验证请求量和事件规模，不是 GPU 数量扩展性。

## 5. 业务拒绝与故障

- KV 拒绝：1 个请求完成，1 个请求因 `kv_or_model_memory_exceeded` 被拒绝。
- 副本故障：4 个请求中 3 个完成，1 个因 `node_down:n0` 失败。
- 故障场景忽略 1 个旧回调，失败请求生成 token 数为 0。
- 健康副本继续处理后续请求，失败副本不产生新的 token。

服务运行 `completed` 与每个请求成功是两个不同层次。KV 不当准入时拒绝请求，是模型按照约束得到的正确业务结果。

## 可写进报告的结论

1. 在冻结的合成 profile 中，TP2 的平均 TTFT 低于 TP1 和 TP4，说明 TP 大小需要权衡计算切分与集合通信。
2. 不同副本使用不重叠 GPU 时，仍会因共享机架上联互相拖慢。
3. 请求数和请求长度共同影响 KV 与排队；超过最大长度预算时必须拒绝。
4. 副本故障终止在途请求，但不应中断健康副本或留下迟到 token。

## 不应写进报告的结论

- 不写“TP2 在所有真实 GPU 上最快”。
- 不写“得到了 Qwen 实测 TTFT 或 token 吞吐”。
- 不写“实现了连续批处理或 PagedAttention”。
- 不把仿真处理事件数当成 GPU 集群规模扩展结果。
- 不把单次墙钟差异写成统计显著结果。
