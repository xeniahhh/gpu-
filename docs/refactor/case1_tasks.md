# 案例一任务清单：GPT-2 Small 多作业数据并行训练

## 使用方式与交付边界

目标：将“模型如何产生梯度通信、多个作业怎样共享有限 GPU 和链路、故障后如何恢复训练进度”作为一条可运行、可解释、可验证的主线。

本清单直接依据课程 `CourseProjectGuidelines.pdf`：结构、行为编排、语义领域三类复杂性都要体现；最终需要可运行 Git 代码库及 8–12 页架构与复杂性报告。以下任务不是全部“待从零写代码”，而是三位组员接手本轮重构基线后的**阅读核验、补全、实验与答辩责任**。有文件不等于功能已验收，完成状态必须由原始输出确认。

- **A：你——模型、作业语义与最终集成判断。** 负责说明“模型是什么、传什么、故障为何必须整组处理”。
- **B：组员一——资源、网络、调度与性能分析。** 负责说明“路径经过哪里、为什么受限、多个作业怎样相互影响”。
- **C：组员二——接口、可追溯证据、界面与交付。** 负责说明“输入和结果如何关联、权限如何执行、老师怎样复现”。
- **单人**表示可以独立完成并提交；**联调**表示仍由一个人主责，另一个人只提供约定输入或做验收。
- **P0**为主线必须完成；**P1**为主线通过后开展。真实 GPU 测量属于 P1，但模型字节数、约束及状态实验属于 P0。
- **工时**是基于已有重构代码的核验/修补估计，不是从零实现复杂仿真器的承诺。约 A 8.5、B 10、C 10 人时的 P0 工作；另留每人 2 小时联调缓冲。不要同时执行案例二的完整任务清单。

评分简称：**架**=架构 25 分；**复**=复杂性管理 25 分；**域**=领域精确 25 分；**析**=分析权衡 15 分；**码**=代码质量 10 分；**演**=现场演示额外 15 分。简称只表示对应证据，不保证得分。

## A 的任务：模型与训练状态

### D01｜冻结问题和实验边界

- **P0｜A 单人｜0.5 小时｜评分：域、析｜类型：设计核验**
- 输入：课程要求、本清单、`IMPLEMENTATION_CONTRACT.md`。
- 产物：一段最终问题陈述与假设列表，写入正式报告；将“真实训练”“流级仿真”“仿真程序并行”分开命名。
- 验收：能用一分钟解释本项目输入为模型/拓扑/作业/故障，输出为完成时间、资源占用和状态证据；不声称执行了真实模型训练或完整 NCCL。

### D02｜核对模型配置及梯度字节量

- **P0｜A 单人｜0.75 小时｜评分：域、码｜类型：代码核验**
- 输入：GPT-2 Small 配置；`packages/fabric-sim/src/fabric_sim/ddp.py`。
- 产物：模型参数表与参数/梯度统计检查。固定 12 层、hidden=768、12 个头、词表 50257、位置数 1024、绑定词嵌入/输出头；FP32 梯度。
- 验收：参数量 124,439,808；梯度 497,759,232 bytes，约 474.7002 MiB；绑定权重仅计一次。实际建模脚本统计值必须与公式相符；不能因为设置了 AMP 就自动把传输梯度改成 FP16。

### D03｜冻结输入与跨模块合同

- **P0｜A 主责，B/C 联调｜1 小时｜评分：架、复、域｜类型：集成核验**
- 输入：D01–D02、共同实现合同、v2 输入校验器。
- 产物：`SimulationSpec`、模型 profile、job、fault、result 字段表；单位、可选值、上限、错误码和规范化 hash 规则。
- 验收：每个 profile 都标 `DERIVED/SYNTHETIC/MEASURED`；提交后修改页面草稿不会改动已保存 spec；相同输入 hash 相同，影响计算的参数改变后 hash 改变。NaN、负时长、超上限和不存在 GPU 明确拒绝。

### D04｜核对训练阶段及同步依赖

- **P0｜A 主责，B 提供通信接口｜1.5 小时｜评分：复、域、码｜类型：代码核验**
- 输入：D02–D03、B 的 `ring_allreduce`。
- 产物：`ddp.py` 中计算→同步→更新→提交逻辑步的代码走读与对应测试。
- 验收：四卡同步未完成时，任何 rank 都不能先更新或提交下一步；world_size=1 无通信；第一版明确单桶、无计算通信重叠、轮间屏障。不能将理论字节量简单除以任意固定带宽后忽略共享竞争。

### D05｜核对检查点保存与故障回滚

- **P0｜A 单人｜1.5 小时｜评分：复、域、析｜类型：代码核验**
- 输入：D04；`checkpoint_interval`、保存/恢复/重建耗时、故障脚本。
- 产物：正常和故障状态机；检查点故障测试。
- 验收：保存完成后才推进 durable checkpoint；保存中故障回到上一份完整检查点；故障停止整个训练组并保留固定 world_size；没有检查点时从可恢复的初始状态重启。报告显示丢失步数、等待、加载、重算，不只给一个“恢复时间”。

### D06｜阻止故障前的旧事件污染新执行

- **P0｜A 单人｜1.25 小时｜评分：复、码｜类型：代码与负例核验**
- 输入：D05、事件队列、`execution_epoch`。
- 产物：人为构造“故障前计算完成事件迟到”的测试与一条可展示事件轨迹。
- 验收：重启后 epoch 增加；旧 epoch 的计算完成、通信完成及延迟启动事件不会推进步骤、重新占卡或完成作业。取消后的 callback 不会凭空创建下一轮流。

### D07｜运行资源准入与故障实验

- **P0｜A 主责，B 核对分配｜2 小时｜评分：复、域、演｜类型：实验待复跑**
- 输入：D04–D06；E3/E4 样例；B 的资源分配结果。
- 产物：准入、故障有余量、故障无余量、保存中故障的完整输入/事件/指标。
- 验收：八卡上 A4+B2 时 C4 等待；永久显存不适配明确不可调度；A4+B4 损失两卡后不能同时维持两个四卡作业；未受影响的作业不被免费迁移。无论仿真结局如何，程序都要给出明确终态或截止原因。

### D08｜获取 3090 实测 profile（主线通过后）

- **P1｜A 单人，可请 B 复核计时｜2 小时起｜评分：域、析｜类型：真实 GPU 待执行**
- 输入：可用 PyTorch/CUDA 环境、同一模型配置、明确 GPU ID；不要为了跑测量更改整台服务器驱动。
- 产物：参数/梯度统计、前后向与优化器时间原始样本、显存 allocated/reserved 峰值及余量处理、软件版本。
- 验收：预热、CUDA 同步计时；合成数据/随机初始化只用于系统负载；测量失败则保留 `SYNTHETIC` 标签。单机 3090 数据不能直接校准跨机架 Leaf–Spine。

## B 的任务：网络资源与调度

### D09｜核对拓扑与物理资源映射

- **P0｜B 单人｜1 小时｜评分：架、域｜类型：代码核验**
- 输入：D03、`core.py`、四节点各两卡合成拓扑。
- 产物：资源路径示例表：同节点、同机架跨节点、跨机架三类。
- 验收：本地通信使用有限共享资源；跨节点消耗源/目的 NIC，跨机架还消耗对应方向上联；同一 NIC 不因多 GPU 而凭空倍增容量；双向链路容量口径明确。图上不得把单机八卡画成八台实测服务器。

### D10｜验证 Ring 两阶段和解析参考

- **P0｜B 单人｜1.5 小时｜评分：域、码｜类型：代码与实验核验**
- 输入：D02、`core.py`；E0：四 rank、64 MiB、100 Gbps 独立方向资源、零延迟。
- 产物：E0 原始结果及单元测试。
- 验收：ReduceScatter/AllGather 各三轮，每 rank 六次各 16 MiB，总 96 MiB；无竞争解析时间约 8.05306368 ms。测试量不是模型 profile，不写成 GPU 测量。发送/接收不得重复计入单向传输量。

### D11｜验证事件推进和动态容量共享

- **P0｜B 单人｜2 小时｜评分：复、域、码｜类型：代码核验**
- 输入：D09–D10、活动流、剩余 bytes、事件优先级。
- 产物：共享瓶颈、流中途完成、启动延迟、零容量与 horizon 的测试。
- 验收：每次活跃集合变化后重算速率；任何方向总速率不超容量；剩余 bytes 不为负；失败与完成同时间的次序固定；到达 horizon 不死循环。若采用保守均分，要说明它可能留下带宽，不自称最优 max-min。

### D12｜验证显存准入和成组分配

- **P0｜B 主责，A 定义作业语义｜1.5 小时｜评分：复、域、码｜类型：代码核验**
- 输入：D03、GPU 所有权、world_size、显存 profile。
- 产物：准入原因码及 GPU 所有权断言。
- 验收：所有 GPU 原子预留或一张也不占；运行作业恰好拥有 R 张健康且显存合格的 GPU；永久不适配与暂时资源不足分别表示；队列规则、是否抢占/回填明确。DDP 显存不能按 R 平均。

### D13｜运行放置与共享竞争实验

- **P0｜B 单人｜1.5 小时｜评分：域、析、演｜类型：实验待复跑**
- 输入：E1/E2；固定模型、步数、rank 数、路径策略；A/B 使用互不重叠 GPU。
- 产物：紧凑与分散放置的路径/字节表；A 独占、B 独占、A+B 并发的链路曲线和完成时间。
- 验收：共享瓶颈在轨迹中真实出现；并发 slowdown 的分母对应相同独占任务；逻辑总通信量相同，但物理路径负载不同。不能为了让 RailAware 获胜而改变其它条件。

### D14｜检查节点及链路故障的影响范围

- **P0｜B 主责，A 联调恢复｜0.75 小时｜评分：复、域｜类型：集成核验**
- 输入：D05、节点/资源故障、作业完整通信路径。
- 产物：故障影响集合与原因说明。
- 验收：故障发生时即使作业正在计算，只要其分配或后续通信路径已不可用，也应有一致处理；失效资源不被再次分配；无关作业可以继续；资源修复后准入规则重新评估。

### D15｜比较策略并解释代价

- **P0｜B 单人｜1 小时｜评分：析、域｜类型：分析核验**
- 输入：D13 结果、当前可用的 `first_fit/compact/spread` 等策略。
- 产物：策略对照表，包含全部作业完成/等待时间与瓶颈解释。
- 验收：按代码实际支持的策略命名，不把旧 rail 标签当新物理带宽；不保证某策略在所有样例获胜。优先级或紧凑放置收益如以他人等待为代价，必须同时呈现。

### D16｜分析规模与敏感性

- **P0｜B 单人｜0.75 小时｜评分：析、码｜类型：性能分析**
- 输入：事件数、流数、仿真器 CPU 耗时；小/中规模配置。
- 产物：至少三档规模的输入、事件计数、内存/输出大小或 CPU 时间；带宽敏感性小表。
- 验收：模拟的训练耗时和程序真实 CPU 耗时分列；固定同一训练工作量；确定性仿真反复跑同样输入不生成虚假置信区间。超过当前资源/步数上限明确拒绝。

## C 的任务：接口、证据与展示

### D17｜验证提交、查询与错误合同

- **P0｜C 单人｜1.5 小时｜评分：架、复、码｜类型：接口核验**
- 输入：D03、`simulation_api.py`、v2 scenarios。
- 产物：POST 202 与 GET 状态/结果/事件的真实 HTTP 记录；输入错误与队列满的记录。
- 验收：有效提交得到 ID/hash；查询在运行中可用；格式错误 422，繁忙状态有明确响应；“作业不可调度”与“仿真服务器出错”不混淆。HTTP 成功不等于每个业务作业都完成。

### D18｜验证快照和持久记录

- **P0｜C 单人｜1 小时｜评分：复、码｜类型：存储核验**
- 输入：D17、SQLite run 记录。
- 产物：修改草稿不影响已提交记录的测试；服务重启后终态/中断态测试。
- 验收：保存完整输入、hash、结果、事件；重启遗留运行进入明确 interrupted 状态，不承诺自动续跑；结果始终指向原快照。导出数据不含 bearer token 或本机凭证。

### D19｜验证身份、权限及输入边界

- **P0｜C 单人｜0.75 小时｜评分：复、码｜类型：安全核验**
- 输入：已有 viewer/editor 策略、v2 路由。
- 产物：匿名、viewer、editor 的状态码矩阵及测试。
- 验收：viewer 可读和解释结果，不能新建仿真或更改输入；未知 ID 有明确错误；请求大小和数值上限生效。说明这是服务级共享角色，无个人账户/多租户隔离；仿真故障不能触发真实系统命令。

### D20｜验证 Assistant 的证据引用

- **P0｜C 主责，A/B 各复核一个解释｜0.75 小时｜评分：复、域、演｜类型：功能核验**
- 输入：E2–E4 已保存结果与事件。
- 产物：三条问答：“为什么慢”“为什么等”“故障后丢了多少进度”。
- 验收：解释引用实际 job/resource/event/指标；证据不足则明确说明；不改变结果或调度；明确是规则驱动的只读解释，而非已接入大模型 Agent。

### D21｜完善可操作演示界面

- **P0｜C 单人｜1.5 小时｜评分：架、演｜类型：界面核验**
- 输入：`apps/web/workload.html`、D17–D20。
- 产物：场景选择、参数输入、状态时间线、指标、带宽曲线与假设说明。
- 验收：可以从页面完成 E2/E4，无需复制服务器日志才能看懂；图示单位一致；显示 SYNTHETIC/MEASURED 来源；事件回放标明“仿真回放”，不冒充真实 GPU 动态监控。

### D22｜制作架构、数据和状态图

- **P0｜C 主责，A/B 各核对相关边界｜1 小时｜评分：架、复｜类型：报告产物**
- 输入：最终代码而非旧架构设想。
- 产物：组件图、数据对象/关系图、训练状态机、一次故障恢复时序图；源文件可编辑。
- 验收：图上组件都有对应代码；图上主路径不出现未接入的 NATS/JetStream/多机训练；输入快照与运行状态分开；图中“工作进程”注明是仿真执行还是训练 rank。

### D23｜形成 8–12 页正式报告与答辩材料

- **P0｜C 整理，A/B 各交自己的原始小节｜2 小时｜评分：架、复、域、析｜类型：联合交付**
- 输入：D01–D22 的已验证结果、课程模板、`rubric_mapping.md`。
- 产物：8–12 页 MD/PDF 报告、PPT 更新清单、每人负责的技术问题与回答。
- 验收：覆盖 Executive Summary、问题、架构/数据/状态、三类复杂性、执行证据、规模和权衡、未完成工作；每个数值有输入与来源；截图不替代原始结果。两位组员应各解释至少一个约束反例。

### D24｜干净环境复现与五分钟演示

- **P0｜C 主责，全员验收｜1.5 小时｜评分：码、演｜类型：交付核验**
- 输入：最终代码、依赖清单、入口命令、证据包。
- 产物：干净目录启动记录、Git 仓库链接/提交号、测试摘要、短录屏、三人发言分工。
- 验收：另外一人按 README 可启动并复跑主线；提交仓库排除 .env/token/数据库凭证；录屏覆盖正常、共享竞争、资源等待、故障回滚；演示异常时可用同版本录屏和结果解释。仓库发布与访问权限需要由组员实际检查，不将本地目录当已托管仓库。
