## 3. 三类复杂性要如何体现

| 维度 | 旧模式容易出的问题 | 重构采用的抽象 | 验证方法 |
|---|---|---|---|
| 结构复杂性 | 模型、放置、通信和页面逻辑互相混用，改一个场景牵动所有模块 | 公共拓扑/事件引擎 + DDP/TP 两个场景 adapter + 独立应用服务 | 同一网络引擎可承载两种工作负载；无 CUDA 的核心测试；输出合同一致 |
| 行为/编排复杂性 | 资源不足仍启动、故障前事件推进新执行、保存中断却使用半份 checkpoint | 成组分配、明确状态机、epoch、不可变 run 快照、明确终态 | 资源不足、迟到事件、保存中故障、TP 副本失败等负例 |
| 语义/领域复杂性 | 把任意 ring 当完整训练、把激活当梯度、把权重显存当峰值、把单机当跨机架 | 模型 profile、通信阶段与字节、方向资源与有效带宽、DDP/TP 显存规则 | 参数/字节手算校验、TP 合法性、KV边界、同机有限通路、模型假设标签 |

## 4. 建议的 10 页正式报告分配

| 页 | 内容 | 提供者 | 必须出现的材料 |
|---|---|---|---|
| 1 | 封面信息与 Executive Summary | A | 题目、路线、真实成员、Git URL、问题、核心复杂性及解决方法 |
| 2 | System Domain & Problem Statement | A | 真实场景、模型、输入输出、规模、约束；为何朴素方案不足 |
| 3 | High-Level Component Architecture | C | 实际组件图及控制/领域计算边界 |
| 4 | Data Models & Schema Design | A/C | 输入 profile/spec、运行状态、结果关系；核心 API/contract |
| 5 | Behavioral State Machine & Control Flow | A/C | 正常与故障状态机、关键时序、epoch/快照 |
| 6 | Complexity Management Evaluation | B 汇总 | 三类复杂性问题、抽象及可核验证据表 |
| 7 | Implementation & Execution | C | 启动、API/角色/Assistant、持久化与日志实例 |
| 8 | Verification & Experiments | A/B | 解析/约束校验、共享竞争、故障实验及原始记录路径 |
| 9 | Scaling & Trade-off Analysis | B | 规模、参数敏感性、策略代价、仿真与实测边界 |
| 10 | Conclusion、Future Work、References | A/C | 已实现/未实现、局限、安全风险、来源；必要附录可扩展至 12 页 |

课程模板中的英文小节可以保留，正文用自然中文。8–12 页是报告要求，不是每页 PPT 的数量。PPT 采用面向讲解的取舍；报告保存实现细节。若当前只完成一个场景，另一个必须标设计/简化基线，不混进主实验结论。

## 5. 用户给出的汇报项目逐项对齐

| 汇报要求 | 应如何落地 |
|---|---|
| 设计思想 | 以具体模型工作负载产生通信，再由共享资源和状态约束推导结果 |
| 项目分工 | A 模型/语义，B 资源/网络，C 应用/证据；使用两份任务清单的 ID 追踪贡献 |
| 软件架构 | 只画实际接入路径；旧静态 v1 与新动态 v2 分开标注 |
| 核心模块、API、contract | 拿一个请求从冻结 spec 到结果的实际字段示例；说明单位、版本、错误码 |
| Assistant | 只读、基于结果与事件的规则解释；不冒充未接入的 LLM Agent |
| 认证/权限 | 展示 viewer/editor 行为差异，并说明当前无个人身份和租户隔离 |
| 性能/扩展性 | 仿真时长和真实 CPU 耗时分列；说明事件数、输出规模和请求上限 |
| 未实现内容 | DDP 多桶重叠/弹性训练；TP 连续批处理/KV分页迁移；真实网络协议和高可用等 |
| 安全风险 | 共享 token 与租户边界、请求资源消耗、输入校验、导出凭证；不要在报告附真实凭证 |

## 6. 实现状态如何验收和标注

本轮代码基线正在落实共同合同；最终交付以对应脚本输出和测试结果为准，不在此预填“全部完成”。任务清单中的每项应记录：

```text
task_id / owner / status / code_or_config / evidence_path / checked_by / remaining_issue
```

建议状态：`待核验`、`仿真验证通过`、`真实GPU已测`、`失败待修`、`明确延后`。实测状态只能在真实服务器产生记录后更新。不得将“代码已写”“测试已运行”“测试通过”混成一个状态。

| 分类 | 可以据此声称什么 | 不能据此声称什么 |
|---|---|---|
| DERIVED | 由明确结构/算法推导的参数或字节数 | 真实设备耗时与带宽 |
| SYNTHETIC | 给定假设下的仿真结果与敏感性 | 3090 或真实数据中心的实际性能 |
| MEASURED | 对记录配置、设备与版本的真实测量 | 未测部署或更大规模的普遍结论 |
| 自动化测试通过 | 测试覆盖条件下满足已检查规则 | 没有任何未知错误或所有生产场景正确 |

## 7. 交付前硬门槛

- [ ] 核心代码可由另一名组员从干净目录启动，依赖和入口明确。
- [ ] 解析校验、资源约束、状态负例和真实 HTTP/权限测试都留原始结果。
- [ ] 任何失败或截止的业务任务均有原因，没有半份结果冒充完整成功。
- [ ] 模型、通信类型、显存和故障语义可由负责组员用具体数字解释。
- [ ] 图和正文与最终代码一致；没有把未接入的组件画入主路径。
- [ ] 8–12 页报告、可访问 Git 仓库和演示准备完成。
- [ ] 证据文件没有 bearer token、数据库口令或本机凭证。
- [ ] 三个人都能回答“为什么这样设计、替代方案是什么、付出了什么代价”。

## 8. 学术与工程诚实

课程指出可能 Fail 的情况包括工作量单薄、拷贝已有代码、AI 生成材料却不能解释细节、全程读稿。对应措施是：保留设计决策与修改记录，引用依赖和参考资料，每人实际复跑/修改/解释本人模块，用反例验证而非仅展示截图。工具辅助生成代码和文档后仍需组员审阅、测试和理解；不得隐瞒未运行的实测或编造结果。
